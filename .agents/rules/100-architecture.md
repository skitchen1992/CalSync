# Architecture, Modules & Dependency Injection

Stack: NestJS 12 (ESM project generated by `nest new`), TypeScript 6 `strict`, PostgreSQL + Drizzle,
Zod for every schema (env, request input, external responses, LLM output), Vitest. This file
describes the target layout and the module/DI conventions every feature follows.

## Top-Level Layout
```
src/
├── main.ts               # Bootstrap only: create app, logger, helmet, shutdown hooks, listen
├── app.module.ts         # Root composition: infrastructure modules + APP_* global enhancers
├── config/               # Env schema (Zod) + registerAs() namespaces — the only place reading process.env
├── common/               # Cross-cutting, feature-agnostic: errors/, filters/, clock/, utils/,
│                         # common.module.ts (@Global: Clock, later CryptoService). Never imports a feature.
├── db/                   # schema.ts (tables + inferred row types), database.ts (types), database.module.ts,
│                         # drizzle-lock.store.ts (LockStore for @nestjs/locks)
├── integrations/         # One module per external system: google/, deepseek/, telegram-api/
│                         # Narrow, domain-shaped clients. No CalSync business logic.
├── sources/              # Source adapters (ics, caldav, yandex-embed, gsheet) → NormalizedEvent[]
├── sync/                 # Sync engine (diff, apply), dispatcher job, per-source locks
├── bot/                  # Telegram bot entry point: commands, conversations, keyboards
├── auth/                 # Google OAuth flow (authorization URL, callback controller, token storage)
└── health/               # /health endpoint (@nestjs/terminus)
drizzle/                  # Generated SQL migrations + meta/_journal.json (committed)
test/                     # e2e specs; support/ (createTestApp), fixtures/, fakes/
```

## Dependency Direction
```
bot/, auth/ (controllers)  →  sync/, sources/  →  integrations/, db/  →  config/, common/
```
- Arrows point to what a layer may import. Nothing imports "upwards": `integrations/` never imports
  `sync/`, `sources/` never imports `bot/`, `common/` imports no feature at all.
- Entry points (`bot/`, controllers) are thin: they parse input, call one service method and format
  the result. All decisions live in services.
- Module-level cycles are a design bug. Extract the shared piece into its own provider/module instead
  of reaching for `forwardRef()` (see "Circular dependencies" below).

## Feature Module Anatomy
```
src/<feature>/
├── <feature>.module.ts        # @Module: imports, providers, exports (public API of the feature)
├── <feature>.service.ts       # Application logic; orchestrates repositories and integrations
├── <feature>.controller.ts    # Only if the feature has an HTTP surface (see 102-http-layer.md)
├── <feature>.repository.ts    # Drizzle queries, only if the feature owns tables (see 104)
├── <feature>.schemas.ts       # Zod schemas + inferred types (input, external payloads)
├── <feature>.errors.ts        # Domain error classes (see 103-errors-logging.md)
├── <feature>.constants.ts     # Injection tokens (Symbols), fixed limits
├── <feature>.types.ts         # Feature-local types that are not schema-derived
├── <name>.ts                  # Pure logic (parsers, diff, normalizers) — no Nest decorators
└── *.spec.ts                  # Colocated unit tests (see 108-testing.md)
```
- Keep pure, framework-free logic (sheet row parsing, event diffing, time normalization) in plain
  functions in their own files. They are the bulk of the business rules and must be testable without
  a Nest container.
- A feature only has the files it needs. Do not create empty placeholders.

## Modules
- One module per feature or external system. A module encapsulates its providers; another module sees
  only what is listed in `exports`. Export the smallest public surface (usually one service), never
  repositories or SDK clients.
- To use another feature's provider, import its module. Never list another module's provider in your
  own `providers` array: that creates a second instance with its own state.
- `@Global()` is reserved for true infrastructure that almost every module needs (config, database,
  `common/` services such as `Clock`). The Nest docs explicitly warn that making everything global is
  a bad design: it hides dependencies. Feature modules are never global.
- Configurable modules are built with `ConfigurableModuleBuilder`, following the Nest naming
  guidelines:
  - `forRoot()` / `forRootAsync()`: configured once, shared by the whole app.
  - `register()` / `registerAsync()`: a configuration specific to the importing module.
  - `forFeature()`: a per-module refinement of a `forRoot()` setup.

  Always provide and use the `*Async` variant when the options come from config, so that options
  arrive through DI (`inject: [googleConfig.KEY]`) and nothing reads `process.env` directly:
  ```ts
  // google-calendar.module-definition.ts
  export const { ConfigurableModuleClass, MODULE_OPTIONS_TOKEN } =
    new ConfigurableModuleBuilder<GoogleCalendarModuleOptions>().setClassMethodName('forRoot').build();
  ```

## Providers & Dependency Injection
- Use constructor injection with `private readonly` parameters. Do not use property injection,
  do not call `new` on an `@Injectable()` class, and do not use `ModuleRef.get()` as a service locator.
- Non-class dependencies (SDK clients, option objects, lists of adapters) are injected through tokens.
  A token is a `Symbol` exported from `<feature>.constants.ts`, never an inline string literal.
  TypeScript interfaces disappear at runtime, so an interface-typed dependency always needs a token.
- An abstraction with a default implementation is an **abstract class**, which serves as both the
  type and the token: `{ provide: Clock, useClass: SystemClock }`, injected as
  `private readonly clock: Clock`. Prefer this over interface + Symbol.
- Choose the provider form by intent:
  - `useClass`: the default, or to switch implementations (fake vs real).
  - `useValue`: constants and test doubles.
  - `useFactory`: anything that needs construction logic or config, such as SDK clients. Declare
    dependencies in `inject` (mark optional ones with `{ token, optional: true }`).
  - `useExisting`: aliases.
- Multi-implementation registries (for example, source adapters) are a factory provider that collects
  the implementations. Do not discover them at runtime:
  ```ts
  export const SOURCE_ADAPTERS = Symbol('SOURCE_ADAPTERS');

  {
    provide: SOURCE_ADAPTERS,
    useFactory: (...adapters: SourceAdapter[]) => adapters,
    inject: [IcsAdapter, CaldavAdapter, YandexEmbedAdapter, GoogleSheetAdapter],
  }
  ```
- Scope: providers are singletons (default scope). Do not use `Scope.REQUEST` or `Scope.TRANSIENT`.
  Request scope propagates up the whole injection chain, creates instances per request and
  costs performance. It also has no meaning for cron jobs and bot updates. Pass per-call context
  (user id, source id) as method arguments.
- Constructors only store dependencies. No I/O, no async work, no timers in constructors (see
  lifecycle hooks below).

### Circular dependencies
- First fix the design: move the shared logic into a third provider, or invert the call with an
  event or a callback.
- `forwardRef()` is a last resort. Use it only with a comment explaining why the cycle is inherent,
  and never rely on which constructor runs first (the order is indeterminate).
- Do not create barrel files (`index.ts`) that re-export module or provider classes. The Nest docs
  name barrel files as a common source of circular imports that resolve to `undefined`.

## Lifecycle
- Open connections and warm up in `onModuleInit()` / `onApplicationBootstrap()` (Nest awaits async
  hooks). Release resources in `onModuleDestroy()` / `onApplicationShutdown(signal)`.
- `main.ts` calls `app.enableShutdownHooks()`. Without it, shutdown hooks never run on `SIGTERM`
  (Docker stop), so in-flight sync runs and DB pools are cut off.
- In v12, lifecycle hooks run by component hierarchy level. Rely only on the guarantee that a
  provider's dependencies are initialized before it. Do not rely on an ordering between unrelated
  modules.

## Bootstrap (`main.ts`)
`main.ts` does bootstrap only: create the app (with the logger, see 103), apply `helmet()` (see 107),
call `enableShutdownHooks()`, then `listen()`. Global pipes, guards, filters and interceptors are
registered as `APP_PIPE` / `APP_GUARD` / `APP_FILTER` / `APP_INTERCEPTOR` providers in `AppModule`,
**not** with `app.useGlobal*()`. Enhancers registered in `main.ts` cannot inject dependencies, and an
e2e test that boots `AppModule` would not get them.
```ts
// main.ts
import { ConsoleLogger } from '@nestjs/common';
import type { ConfigType } from '@nestjs/config';
import { NestFactory } from '@nestjs/core';
import helmet from 'helmet';
import { AppModule } from './app.module.js';
import { appConfig } from './config/app.config.js';

async function bootstrap() {
  // ConfigModule loads and validates .env while the app is created, so the configured logger can
  // only be built afterwards; bootstrap logs are buffered until then.
  const app = await NestFactory.create(AppModule, { bufferLogs: true });
  const config = app.get<ConfigType<typeof appConfig>>(appConfig.KEY);
  app.useLogger(new ConsoleLogger({ json: config.logFormat === 'json', logLevels: config.logLevels }));
  app.use(helmet());
  app.enableShutdownHooks();
  await app.listen(config.port);
}
await bootstrap();
```
Never read the environment in `main.ts` before `NestFactory.create()`: `.env` is not loaded yet
(see 101).

## ESM & TypeScript Conventions
- The project is ESM (`"type": "module"`, `module`/`moduleResolution: nodenext`). Relative imports
  carry the `.js` extension: `import { SyncService } from './sync.service.js';`.
- Use `import type { … }` for type-only imports (`isolatedModules` is on). Import Node built-ins with
  the `node:` prefix (`node:crypto`).
- `strict` is on and stays on. `strictPropertyInitialization` is off only because DI assigns
  constructor parameters. Do not use `any`. Use `unknown` and narrow it with Zod or type guards.
- Do not use `enum`. Use `as const` objects or string-literal unions (they work with Zod and
  `isolatedModules`).

## Naming
- Files: kebab-case with a role suffix, one main class per file. Examples: `google-calendar.service.ts`,
  `sources.controller.ts`, `sync-dispatcher.job.ts`, `event-diff.ts`, `event-diff.spec.ts`.
- Classes: PascalCase with the role suffix that matches the file (`GoogleCalendarService`,
  `SourcesController`, `SyncDispatcherJob`). Tokens: `UPPER_SNAKE` Symbols.
- Scaffolding with `nest g module|service|controller <name>` is fine. Adjust the generated files to
  these conventions (ESM imports, colocated spec).
